A small fleet is easy to start and hard to keep. Every service on every machine has to be on the right version, an update must not take a host down when it fails, and somebody has to be able to say who changed what. Most small fleets are kept with a loop of ssh commands, and they drift. hostkeeper is one root daemon on each host and one coordinator for the fleet. CI sets the desired version of a service, each host fetches the signed package and runs the service’s own update hook through a fixed contract of steps, and the coordinator rolls a new version out by an update plan of stages.

The problem. Without a tool built for it, hosts end up on different versions, an update is a hand-run loop that stops where a connection drops, a run that stops midway leaves a host half updated, nothing records who changed what, Linux and macOS each need their own scripts, and a restart drops the requests a service was serving.

The hypotheses.

  1. If every host dials out and the coordinator only answers, CI needs no ssh key and no host opens a port.
  2. If a service’s update is a fixed contract of bounded steps, and the daemon records each step before it runs it, a run that stops midway can be finished or undone at the next start.
  3. If a version reaches the hosts of a service stage by stage, the first stage a single host, and the next stage starts only when every host of the one before has updated and baked, a bad version reaches one host first, and a failed verify rolls that host back before the next stage starts.
  4. One daemon, compiled for Linux and for macOS with the differences behind adapters, gives both kinds of host one model, one API and one audit trail.
  5. A hand-off with no dropped requests is the service’s own knowledge, so the hook does it and the contract gives it the steps to do it in.

The solution. The daemon is one Rust binary that runs as root under systemd or launchd and listens on no network port. It enrolls with the coordinator’s certificate authority, and an operator approves it by its key. The coordinator keeps its state in one Postgres database, serves an operator API over gRPC and an HTTP/JSON gateway, a generated command line and a small web UI, and keeps an append-only audit log. CI signs in with its GitHub Actions OIDC token and sets the desired version. The coordinator’s rollout gate orders a new version stage by stage by the service’s update plan, with a canary, a bake, holds, a halt, a fleet-wide force and an automatic rollback.

Where it stands. hostkeeper is early. Its parts are built and tested one by one, and releases are published from main. One canary run on one lab node has enrolled a host and installed, updated and rolled back a demo service with the shipped daemon and coordinator, and the other five Linux nodes of the lab were then adopted and enrolled and given the demo service. The table says what is built; what is not built yet lists what is missing, and what we have measured, and what not yet gives the times and memory of those runs, and the measurements still open.

A few servers, kept by hand: the problem

Take a fleet the size of ours: a handful of Linux servers and a couple of Macs, each running a few long-lived services that other machines depend on. Nothing about it is large, and that is the trouble. It is too small to justify a cluster and its control plane, and too large to update by hand without mistakes. This section shows what keeping such a fleet is like without a tool built for it. Each problem is one that hostkeeper is built to remove, and the figures draw the four that are easiest to miss.

Version drift across hosts, from hand-run ssh loops

The usual update is a loop on an operator’s laptop that runs a script on each host over ssh. It runs hosts one after another, it stops at the first failure (or carries on past it, which is worse), and it updates only the hosts that were reachable and listed. After a few such runs no two hosts are certain to be on the same version, and the only way to know is to log in to each and look.

An update half applied when a run stops midway

An update is several steps: stop the service, unpack the new release, put its files in place, change its configuration, start it. A script that stops between two of them, because a connection dropped, the laptop slept or a command failed, leaves the host in a state that is neither release. Running the script again starts from the top, over a host that is no longer where the script assumes it begins.

No record of who changed what

When a service misbehaves the first question is what changed. With hand-run updates the answer is spread over shell histories on laptops, a chat thread and each host’s own logs, if it was written down at all. A pause on one host, a forced version or an exception made during an incident is known only to the person who made it.

Linux and macOS, each with its own tooling

A Mac runs its services under launchd, a Linux server under systemd. They differ in how a service is defined, started, stopped and inspected, in where its logs go and in how a binary is trusted. Tools that manage Linux servers seldom treat a Mac as a host of the same kind, and tools that manage Macs manage the operating system and its apps, not a fleet’s own services. A mixed fleet ends up with two update paths to write, test and audit for every service that runs on both.

A restart that drops live work

The simplest update stops the old process and starts the new one. Every request in flight when the old process stops is cut, and every request that arrives before the new one is ready is refused. For a service that other machines lean on, a storage front or a build cache, each update is a small outage that its clients see as errors. Avoiding it needs the old and new processes to overlap and hand the listening socket over, and only the service knows how to do that.

What the fleet needed

Put together, the fleet needed one updater for both kinds of host, driven from CI with no ssh key and no inbound port; an update made of named, bounded steps written down before each runs, so a stopped run is finished or undone; an update plan that rolls a version out stage by stage, with a way to hold, force and abort; a hook that the service ships, so a service that can hand over its socket does; and one audit trail of who changed what. It also needed none of this to require a cluster to run. The comparison checks the tools that exist against that list, and the design describes what hostkeeper builds for it.

Why we built it: where existing tools fall short

Before writing an updater we checked the tools that exist against what the fleet needed. This section is that check. Each claim about another tool was read against that tool’s own current documentation, and the page is in the sources; a version is named where the page names one. The hostkeeper column describes main as this report does, including what is built but not wired. The aim is a fair comparison: most of these tools do far more than hostkeeper, and the last part of this section says where one of them is the better choice.

The gaps

The eight gaps are the needs of the problem, each worded so that a tool either documents it or does not:

  • G1 macOS as a first-class host next to Linux, under launchd, in the same model and the same tool.
  • G2 Deploying from GitHub Actions: CI publishes a signed release and sets the desired version, with no ssh key in CI, no inbound access to a host and no person at a terminal.
  • G3 Live updates: a hook contract (prepare, cutover, verify, rollback, cleanup), a hand-off with no dropped requests, and an automatic rollback when verify fails.
  • G4 Fleet-wide safety: a staged update plan per service, holds, force and abort, and a canary.
  • G5 Identity and enrollment: a host known by its hardware (MAC address, with BMC inventory) rather than its hostname, enrolled with a certificate authority and approved by a person.
  • G6 One root daemon per host with its verbs compiled in and no language runtime to install and patch.
  • G7 An API with generated clients and a command line, a simple UI, and an audit trail of who changed what.
  • G8 No cluster control plane to run for a fleet of a few hosts.

  • h1. A daemon runs under launchd on a Mac: a device test starts it and asks its status, and an end-to-end device test enrolls it with a coordinator and installs, updates, rolls back and uninstalls hello’s package, its plists linked into /Library/LaunchDaemons and loaded by launchd. On Linux the unit control runs systemctl; a privileged run starts, reloads and stops a real unit through it.
  • h2. CI authenticates to the coordinator with a GitHub Actions OIDC token on Releases.SetDesired and Releases.Converge, and an operator’s token may also set the desired version. Packages are attested in CI, and hosts only dial out. CI needs network reach to the coordinator’s private listener, not to any host. Releases are published from main as GitHub releases, but no release channel that the daemon reads is hosted: the operator stages and serves one. The shipped daemon’s heartbeat reaches the coordinator over mutual TLS once the host is enrolled, so a desired version reaches it in the reply.
  • h3. The step contract (prepare, cutover, verify, cleanup, rollback), the rollback after a failed verify and the dead-man are built and tested in process. The service’s hook does the hand-off; the daemon does not enforce zero dropped requests.
  • h4. The update plan (stages, a manual advance, pause and resume), the canary, the bake, holds and force are built in the coordinator, and max_updating and min_up pace the hosts of a stage per role. Hosts.Abort reaches every daemon that announces abort-v1; on a host the coordinator cannot reach, root stops the daemon.
  • h5. A host id is chosen by the operator and bound to the host’s key at approval. It is not derived from a MAC address. MAC addresses, serials and the machine id travel as claims that help match an inventory record and authorise nothing. A Linux daemon reads its BMC’s MAC over /dev/ipmi0 and sends it as a claim; a host with no BMC sends none. The CA, approval, renewal and the pinned CA hash are built, and the daemon’s certificate request carries the subject CN=host:pending the CA accepts.
  • h6. One root daemon, in Rust, with its verbs compiled in and no interpreter on the host. Hooks are executables that services ship. The coordinator is a second program.

  • h8. State is in one Postgres database beside one coordinator, each a container on one machine. That is a database to run, but no cluster: there is no failover, and the operator supervises both. The file store the coordinator kept before, plain files with no database, can still be chosen as the way back until it is removed.

G1: macOS as a first-class host

A mixed fleet of Linux and Mac hosts should be kept by one tool and one model. A second tool for the Macs doubles the update path to learn and audit.

  • hostkeeper runs one binary on both systems, with a systemd launcher and a launchd launcher. On a Mac the daemon’s start under launchd, its step jobs, and the linking, loading, rollback and uninstall of a package’s plists are exercised on a hosted Mac after each merge.
  • Salt, Puppet, Chef and Fleet document macOS agents under launchd, in the same model as Linux. Chef lists macOS 14, 15 and 26, Puppet lists macOS 14, 15 and 26 on x86_64 and ARM, and Fleet lists macOS 15 and later.
  • Ansible manages launchd services through a module of community.general, a collection separate from ansible-core, and needs Python on the managed host. Its install guide names macOS only as a control node.
  • Nomad ships macOS binaries and its raw_exec driver runs natively, but its production requirements are Linux-specific and no launchd management was found.
  • Nix tools reach macOS through nix-darwin, which has its own darwin-rebuild; the nixos-rebuild man page names neither darwin nor macOS. deploy-rs has an activate.darwin helper with no documented support matrix, comin and Cachix Deploy support nix-darwin (both need Nix on the Mac, and neither page mentions launchd), and Colmena documents NixOS only.
  • Kubernetes, k3s, Mender, balena and systemd-sysupdate document no macOS hosts.
  • MDM is first-class on Macs and manages no Linux.

G2: deploying from GitHub Actions without ssh keys, inbound access or a person

CI should publish a signed release and set the desired version, and hosts should pull it. Static keys in CI and open inbound ports are the usual weak points.

  • hostkeeper’s design fits: CI’s OIDC token is checked against an allow-list, is good once, and reaches only SetDesired and Converge. Hosts dial out. The gap on main is that the host side is not fully wired (Linux unit control) and no release channel is hosted.
  • Nomad’s documentation shows an OIDC path for CI: its JWT auth method validates tokens against a discovery URL and maps claims to ACL rules. Its pages do not name GitHub, and the runner must reach the servers.
  • Kubernetes can validate external OIDC and JWT tokens in the API server, and GitHub issues per-job OIDC tokens. A pull model needs an add-on such as Flux.
  • Ansible’s ansible-pull is a real pull model that can pin a ref and verify a GPG signature. It needs Ansible on every host, and CI would hold a controller token. We found no OIDC sign-in in the pages read; that is a keyword search, not proof.
  • Puppet and Chef pull from a server, but CI uses a static token or an API key. Salt’s salt-api uses eauth credentials or a token, and its pages mention no OIDC or JWT.
  • Mender, balena and Fleet pull from a server and have CI actions or GitOps, authenticated by a stored token.
  • comin and Cachix Deploy avoid ssh keys and inbound access. comin’s release is a git commit, optionally signature-checked; Cachix’s is started by a vendor-issued activate token that CI holds. Neither documents OIDC.
  • systemd-sysupdate pulls signed manifests from static storage, but has no CI step and picks the newest version.
  • nixos-rebuild --target-host is ssh push, and the man page says the remote host needs to be reachable over ssh. Its system.autoUpgrade module is a pull mode: a systemd timer rebuilds from a flake or a channel, with no OIDC, no desired version set by CI and no signature check. deploy-rs and Colmena are ssh push.

G3: live updates with a hook contract, a hand-off and automatic rollback

A service update should have defined phases, so that a failed verify restores the old version without dropping requests. Most tools run tasks or swap images and leave this to scripts.

  • hostkeeper defines prepare, cutover, verify, cleanup and rollback, with bounded steps, a dead-man, crash resume and a rollback on a failed verify. The hand-off is the hook’s: tierstore’s hook starts a second instance at cutover that takes the listening sockets from the first, which drains, and tierstore’s own tests show the take-over refusing no connection; on macOS its hook restarts the job, with a gap. The daemon does not enforce a hand-off, and the path does not yet run end to end on main.
  • Mender has the closest contract, with update-module states that include ArtifactInstall, ArtifactCommit and ArtifactRollback. Rollback runs only if the module declares SupportsRollback, and the pages describe no zero-downtime hand-off.
  • balena has a real container hand-over strategy: the new container signals readiness by creating a file, with a 60 s default timeout. Rollback on a failed verification is not documented.
  • Nomad has health-gated updates with auto_revert and canaries. Its lifecycle block orders tasks inside an allocation and defines no cutover or verify contract.
  • Chef Habitat has hooks and rolling updates, but no documented automatic rollback in the pages read.
  • Kubernetes has PreStop and PostStart hooks and rolling updates; a DaemonSet rollback is manual.
  • deploy-rs rolls back automatically if the host does not confirm, which checks reachability only. Cachix Deploy runs a rollbackScript and rolls back if the agent loses its backend.
  • nixos-rebuild switches to a new generation, can go back with --rollback or from the boot menu, and defines no hook contract or automatic rollback on a failed check.
  • Ansible, Salt, Puppet, Fleet and MDM run tasks. Salt has onfail and prereq, and Ansible has block and rescue, but any prepare, cutover, verify and rollback sequence is written per playbook or state. systemd-sysupdate keeps old versions and has a boot-assessment fallback only for boot-entry targets, with no per-service hooks.

G4: fleet-wide safety

On a small fleet one bad version should not reach every host. That needs a staged rollout, operator holds, a way to force or abort, and a canary.

  • hostkeeper rolls a service out by an update plan of stages (by default four, the first a single host and the last every eligible host), each stage done only when its hosts have updated and baked, with a manual advance, pause and resume, a canary count, holds, force and an automatic rollback. The hosts of a stage update in parallel up to the desired state’s max_updating per role, and by default one service’s rollout is live at a time. An abort does not reach the shipped daemon.
  • Nomad (max_parallel, a canary count), Kubernetes (maxUnavailable, OnDelete), Ansible (serial), Salt (batch, subset) and Mender (phased rollouts, abort) throttle a run or a job and stage it like a canary. The pages read describe no fleet-wide single-flight lock with hold, force and abort verbs. Ansible’s ansible-pull page says runs are not designed to be concurrent and tells users to add locking.
  • Cachix Deploy’s changelog lists a lock so that only one deployment is active at a time; no hold, abort or canary was found.
  • Fleet groups, Jamf smart groups, balena’s per-device pinning and Colmena’s tags allow a manual canary.
  • nixos-rebuild documents no fleet coordination (--target-host acts on one host per run), and systemd-sysupdate is single-host.

G5: hardware identity and enrollment with a CA and operator approval

Hostnames get reused and cloned. A host should prove which machine it is, and a person should approve it.

  • hostkeeper binds a host id to the host’s key at approval, with a CA that issues short-lived client certificates. Claims (MAC addresses, serial, machine id) are matched against an operator’s inventory of MAC addresses, BMC MACs and serials, and by design authorise nothing. A Linux daemon claims its BMC MAC too (h5).
  • Mender identifies devices by identity attributes, a MAC by default, with accept and reject states. Fleet uses hardware identifiers and enroll secrets. MDM ties enrollment to Apple hardware serials through Automated Device Enrollment and issues certificates over SCEP.
  • Puppet has a CA with manual signing of requests, though the identity is the certname. Kubernetes has CA-signed node certificates with approval of requests, with the identity from the node name.
  • Salt has key acceptance by an operator, with the minion id as the identity. It has an ipmi module and a BMC extension, but they are modules that use supplied credentials, not a built-in identity.
  • Ansible, Chef, balena and Nomad identify hosts by inventory names, client names or generated ids. Nomad also documents client introduction tokens.
  • The Nix ssh tools identify hosts by ssh destination. The Ansible G5 verdict is no†: we found no hardware-keyed identity in the pages read.

G6: one root daemon per host and no language runtime

Fewer moving parts on each host means less to patch and less to attack.

  • hostkeeper is a single compiled root daemon. Hook executables are supplied by each service.
  • Puppet and Chef each run a bundled Ruby on every host, and Puppet Enterprise adds a second agent for orchestration. Salt’s minion is a Python application with a bundled interpreter. Ansible needs Python and ssh on managed hosts.
  • Kubernetes needs a kubelet and a container runtime. Mender, balena and Fleet run one agent but add pieces beside it (update-module executables, a container engine, osquery).
  • The Nix ssh tools and systemd-sysupdate leave no extra daemon on the host, and have no resident service with verbs either; the verbs of the ssh tools are shell commands run as root.
  • MDM uses the Mac’s built-in client, usually with other management agents beside it.

G7: an API, generated clients and a command line, a UI, an audit trail

An operator should see every host and know who changed what.

  • hostkeeper has gRPC and an HTTP/JSON gateway over the same methods, a command line generated from the protos, a web UI and an append-only audit log. Every method is served, and a desired version set by CI is not itself an audit entry (h7).
  • Fleet matches the shape: a REST API, a command line, a UI and an activity feed; its streaming of activities is a Premium feature. Puppet Enterprise has an API, a console and an orchestrator command line, and its activity service covers RBAC changes and orchestrator runs, not code deploys or classification (note h).
  • Ansible has an API and a UI only in AWX and Automation Platform (note g). Salt has an HTTP API and an event stream, but we found no UI or attributed audit in its open-source pages.
  • Nomad has a UI and an API with ACLs, and its audit logging is Enterprise-only. Mender’s audit logs are Enterprise-only. Jamf’s change-management log exports to a file or syslog only on premises, and Jamf Cloud log streaming is a premium add-on.
  • Kubernetes has client libraries and an audit log (off unless a policy is set), and its official Dashboard repository is archived.
  • The Nix tools are command-line only.
  • None of the tools reviewed documents clients generated from one schema end to end; we did not confirm it for any of them.

G8: no control plane for a small fleet

A fleet of three hosts should not need Kubernetes or a database to operate.

  • hostkeeper keeps its state in one Postgres database beside its one coordinator: a database to run, though no cluster, and with no failover; the operator must supervise both (h8).
  • nixos-rebuild, deploy-rs, Colmena, systemd-sysupdate and comin document no control plane. Salt’s open-source master is a single service with no external database in the pages read, though it is a server to run and scale.
  • Kubernetes (k3s on SQLite) and Nomad both need a server tier that must be kept up. Ansible’s UI and audit tier (AWX) runs on Kubernetes with PostgreSQL.
  • Chef Infra Server and Puppet Enterprise need a server with PostgreSQL. Fleet needs MySQL and Redis. Mender’s production path is Kubernetes with MongoDB, NATS and object storage.
  • Cachix Deploy is a hosted backend that agents connect to. balenaCloud, Jamf Cloud, Fleet’s cloud service and hosted Mender likewise remove the control plane at the price of a hosted dependency.

Where another tool is the better choice

Ansible. Better for general configuration management and orchestration where ssh access and Python already exist and rollouts are supervised by a person. It has a large module library, agentless operation and a huge community, and with Automation Platform it adds RBAC, an activity stream and a mature UI.

Salt. Better for a resident, event-driven system with fast fan-out and targeting by grains. It has a first-party macOS minion and needs no database for the open-source master, and it covers remote execution and declarative state far beyond updating a service.

Puppet. Better for continuous convergence of a large, varied fleet, where its module ecosystem, declarative resources, reporting and RBAC justify a server and a Ruby runtime. It supports current macOS releases.

Chef. Better for teams that want a programmable Ruby DSL with deep cookbook coverage, policy versioning and compliance scanning. Habitat is a real packaging and supervision system for Linux and Windows application fleets. Chef Infra Server is scheduled for end of life, so a new adopter would be evaluating Chef 360.

nixos-rebuild, deploy-rs, Colmena, Cachix Deploy and comin. For a fleet that is already NixOS (or nix-darwin) and described in a flake, these are better than a new updater. They bring atomic generations, rollback and nothing extra to run; system.autoUpgrade adds a pull on a timer, deploy-rs adds magic rollback, Colmena adds parallel deploys selected by tag, and comin and Cachix Deploy add pull mode. They do not suit hosts whose services are not built by Nix.

Kubernetes and k3s. Better when the fleet is Linux and the workloads are already containers. They bring declarative reconciliation, RBAC, OIDC authentication, audit and mature clients. A host updater is the better fit only with macOS hosts, native host services or no appetite for a control plane.

Nomad. Better for mixed workloads that need bin-packing, placement and service discovery, or for a team that already runs Nomad. Its health-gated rolling updates with canaries and auto_revert, and its JWT and OIDC sign-in, are a richer deployment engine than hostkeeper’s.

systemd-sysupdate. Better for Linux hosts whose unit of update is a whole OS image, partition or extension tree. It is already on the host, verifies signed manifests, keeps older versions and needs only static hosting. Its man page calls it experimental.

Mender. Better for embedded and IoT Linux fleets that need full-image A/B updates with bootloader rollback, delta updates, Yocto integration, large fleets, phased rollouts and hosted support. Its audit logging is Enterprise-only.

balena. Better for fleets of containerised apps on single-board computers and gateways. It offers a managed dashboard, delta image updates, a prebuilt balenaOS and a built-in hand-over strategy for container swaps with no downtime.

MDM (Jamf Pro, NanoMDM). For Mac device and OS management (enrollment, configuration profiles, OS update enforcement, FileVault, app distribution), MDM is the right and often the only supported channel. Jamf Pro is mature and supported. NanoMDM is a small open-source core to build on, but it needs your own SCEP server and APNs certificate, and MicroMDM’s README says it is in maintenance mode and points to NanoMDM. hostkeeper does not replace MDM on a Mac: it updates the fleet’s own services beside it.

Fleet (osquery). Better for visibility, security and compliance across a mixed fleet of laptops and servers. It brings osquery queries and live inventory, policies, vulnerability reports, Mac MDM, GitOps configuration and large-scale operation, and it is a much broader product than an updater.

So why build hostkeeper. No tool we checked meets G1, G2 and G3 together for native services on Linux and macOS: the tools strong on macOS (Salt, Puppet, Chef, Fleet, MDM) run tasks rather than a hook contract and authenticate CI with a stored token, the tools with a real update contract or hand-off document no macOS hosts (Mender, balena, Kubernetes) or no launchd management (Nomad), and the Nix tools need every service built by Nix. hostkeeper is the narrow tool for that intersection, small enough to run without a control plane, and the column above says honestly how much of it runs on main today.

The design, as it is on main

hostkeeper is one root daemon per host and one coordinator for the fleet. It knows no service by name: each service ships an update hook in its own package, and the daemon runs that hook through a fixed contract of steps (design: Problem, goals). This section describes the code on main. Every claim links to the code or to the section of the design that states the intent, and where the design says more than the code does, this section follows the code and says what is missing.

Two programs

Two programs are built (crates/hostkeeper, crates/hostkeeper-coordinator):

  • hostkeeper, the host program. Its one verb is daemon (crates/hostkeeper-daemon/src/cli.rs).
  • hostkeeper-coordinator serve, the coordinator, shipped as a tarball and a container image (packaging/container/Dockerfile). No systemd unit for it is packaged, so the operator supervises it.

Both programs take their configuration from flags and files, not environment variables. The only environment reads are platform-set: systemd’s NOTIFY_SOCKET and WATCHDOG_USEC, for --notify-systemd.

Architecture

The coordinator has two TLS listeners (crates/hostkeeper-coordinator/src/config.rs, design: The coordinator):

  • the heartbeat listener serves the agent API, hostkeeper.agent.v1.Coordinator, with Heartbeat, Enroll, Poll and Renew, and the frozen JSON heartbeat route. A heartbeat needs a client certificate that names a host. Enrollment is switched on by the CA’s flags (--ca-key-file and its companions, and --enrollment-dir on the file store); then Enroll and Poll need no certificate, because the caller proves it holds its key. Without it they answer UNAVAILABLE and every connection needs a client certificate.
  • the private listener serves the operator API (hostkeeper.operator.v1), the HTTP/JSON gateway over the same methods, a few frozen JSON routes kept for compatibility, and, with --ui-dir, the web UI’s files. It refuses a wildcard address, so it binds one interface.

Its state is in one Postgres database, named by --database-dsn-file, a secret file that holds the connection string. Its tables hold the desired state, every operator change (exclusions, labels, halts, holds, host groups and minimum versions, uninstall intents, bad marks, the last good version, the inventory), the spent CI token ids and acknowledged verdicts, the enrollment store and an append-only audit table. The coordinator takes the database’s advisory lock at start, so a second coordinator on the same database refuses to start, and the database refuses a commit from a session that does not hold the lock. A change that raises protection (a halt, a bad mark, a pause) is kept in memory while the database cannot be reached, and listed in the file --halt-marker-file names until it lands (docs/operations/coordinator-state.md, design: coordinator storage). The file store it moved from is still built and can be chosen instead, as the way back, until it is removed: the desired state in --state-file, the operator’s changes in the ops file with the halts file and an append-only audit file beside it, and an exclusive lock file. hostkeeper-coordinator export writes the database’s state back into files; no verb converts the file store into a database. The fleet itself (each host’s last heartbeat, outstanding orders, bake counts) is in memory and is rebuilt from heartbeats after a restart (design: State).

The daemon is one root process. It listens on no network port and always dials the coordinator, so the coordinator never connects to a host (design: The design in one picture). Its one trust root is the root-owned config /etc/hostkeeper/hostkeeper.toml. That file names the coordinator’s address, the SHA-256 of the fleet’s CA certificate (ca_sha256), the release channel, the trusted signers and the daemon’s bounds. A strict loader refuses unknown keys (crates/hostkeeper-config/src/daemon.rs). The coordinator cannot change it. The daemon serves nothing on the host: it binds no socket. A host’s status, an abort and the clearing of a step record that does not read go through hkctl (hosts get, hosts abort, hosts clear-record); with the coordinator unreachable, root stops the daemon and renames the record by hand (docs/admin.md).

The heartbeat link. The heartbeat client is in crates/hostkeeper-link, with gRPC over mutual TLS (GrpcMtlsLink), a JSON form and one that negotiates between them. Each call is bounded to 10 s. The shipped daemon uses the negotiating one: host_links gives the heartbeat loop HostLink, which makes it at the first heartbeat of an enrolled host, to the config’s coordinator, pinned to its ca_sha256, with the certificate and CA bundle of the pki directory (crates/hostkeeper-daemon/src/cli.rs, crates/hostkeeper-daemon/src/links.rs). Both loops are wired and talk to the coordinator. The loop runs the update, force, install, uninstall and abort orders, the abort beside the order it stops, and announces install-v1 and abort-v1, the features the coordinator requires before it sends an install, an uninstall or an abort (crates/hostkeeper-link/src/beat.rs, crates/hostkeeper-link/src/heartbeater.rs).

Identity and enrollment

What a host’s identity is. A host is named by an operator-chosen host id (a DNS label of at most 63 bytes of a-z0-9-, crates/hostkeeper-wire/src/names.rs). The id is bound to the host’s own key by the SHA-256 of that key, at the moment an operator approves the request. The identity is not derived from a MAC address. MAC addresses, the DMI serial, the machine id and (on a Mac) the serial number and platform UUID travel as claims. Claims help an operator recognise the machine and match it against the inventory, but they authorise nothing (crates/hostkeeper-enroll/src/claims.rs, crates/hostkeeper-coordinator/src/inventory.rs).

The inventory is a table the operator keeps (Enrollment.AddRecord, ListRecords, RemoveRecord, and the UI’s Inventory page): host id, role, data MACs, BMC MAC, serial and notes, at most 10,000 records. Enrollment.List marks each pending request as matched, unmatched or ambiguous against it. A match fills the approval form; only an exact, uncontested match of an open, unused record that names a role is approved by the coordinator itself, within the record's window and once. A request matching one record is approved under that record's host id, and another host id needs replace. An enrolled host is matched the same way, by the claims of the request its key was approved from: Hosts.Get and Hosts.List answer the record it matches with that record's MACs and serial, and when the host was approved, and ListRecords marks each record a host is enrolled against and can list only those or only the others. A Linux daemon reads its BMC’s MAC over /dev/ipmi0 and sends it as a claim; a host with no BMC sends none (crates/hostkeeper-daemon/src/ipmi.rs, design: Enrollment and remote install).

The CA is a module of the coordinator, not a separate process (crates/hostkeeper-enrollment/src/ca, docs/enrollment-coordinator.md). Its key is one P-256 PKCS#8 file of mode 0600 (--ca-key-file), made once with --ca-init. Its self-signed certificate is valid for 20 years, and every daemon pins its SHA-256. It issues host client certificates (subject CN=host:<id>, client authentication only) valid for 7 days, and the coordinator’s own server certificate, valid for at most 90 days. The server certificate is remade when it is missing or in the last third of its life: at the start, and while the coordinator runs, at each look of the reload tick (--tls-reload-secs), so a coordinator that stays up is not left serving an expired certificate. A renewal that fails leaves the certificate in use served, logs at error level, shows its reason in the status, and is tried again at the next tick. Rotating the CA and revocation lists are not built. The CA's key is backed up by a written procedure (docs/operations/ca-backup.md); the rest of the coordinator's state, the enrollment store with it, by dumps of the database: the compose deployment (docs/deploy/coordinator/README.md) dumps its own Postgres on a timer and has the restore and its drill, and a shared server, as the lab’s is, is backed up by that server’s own administrator; and on the file store by hostkeeper-coordinator backup and restore (docs/operations/coordinator-state.md).

The steps, in the code (crates/hostkeeper-enroll, crates/hostkeeper-coordinator/src/enrollment):

  • The daemon checks the coordinator’s CA against ca_sha256 before it sends anything. It then makes a P-256 key, writes it durably, and posts Enroll. A reposted key is the same request.
  • It polls every 5 s (each call bounded to 30 s). A poll is signed over a fresh nonce of 32 bytes, so polling needs no clock. The host does need a correct wall clock: it refuses a certificate that is not valid now, and it decides renewal and expiry by that clock. At most 256 requests may be pending (--max-pending-enrollments). A request no operator approves within 72 hours (--enrollment-request-ttl) expires at the next reload tick: its host is unenrolled, the request is no longer approved and no longer counts as pending, and the host’s key posted again waits anew.
  • An operator approves with Enrollment.Approve, giving the request id, the key hash shown by Enrollment.List, the host id, the role, the host group the host joins and a reason. The approval is one durable write, followed by an audit entry (enroll_approve, or enroll_replace) and a host-group entry. The certificate is made at the next signed poll, once per request.
  • The daemon checks the certificate against the pinned CA and its own key, then stores it as a new generation under /etc/updater/pki with a current link.
  • From half its life the daemon renews over mutual TLS with no operator step. A host that was away past expiry posts a new request for the same host id with the same key, and an operator approves it again.

A request is marked DUPLICATE_CLAIM when it presents a machine id, or a globally unique MAC, already bound to an enrolled host, as a re-imaged or cloned machine does; it is approved only with replace. Approve with replace moves a host id to a new key, after which the old key’s certificate no longer identifies the host. There is no operator call to deny or retire a host. The coordinator has the deny and retire states, but nothing outside its tests writes them. Mac auto-approval by a one-use MDM nonce (valid 3600 s) is built in the coordinator’s library. With --mdm-api-url, on the file store only for now (the gate keeps its records beside --enrollment-dir), the coordinator’s device check is the MDM gate’s record of each device (crates/hostkeeper-mdm-gate), and with its enrollment side the gate installs the config profile and pushes a nonce bound to the Mac’s pending request, which the daemon posts back with that request; the gate does not install the pkg yet.

The daemon’s certificate request. The daemon builds every certificate request, for Enroll and for Renew, with the one subject CN=host:pending (crates/hostkeeper-enroll/src/key.rs, csr_der): the CA’s profile accepts only a subject that is exactly one CN=host:<id> (crates/hostkeeper-enrollment/src/ca/profile.rs, check_request) and refuses anything else as bad_csr. The id is assigned at approval, and the CA never takes it from the request: the certificate’s subject is always the approved id. An earlier daemon sent an empty subject, which the CA refused, so no daemon could finish enrollment. The tests in crates/hostkeeper-enroll/tests/enroll/coordinator.rs hold the daemon’s own requests to the CA’s profile, and drive the daemon’s enroller against the coordinator’s own enrollment and CA through approval, the first certificate and its renewal.

The two APIs

Every API is a protobuf service in crates/hostkeeper-proto, compiled in pure Rust with nothing generated checked in (design: The operator API):

  • hostkeeper.agent.v1: Coordinator with Heartbeat, Enroll, Poll and Renew;
  • hostkeeper.operator.v1: Hosts, Releases, Services, Enrollment and Audit;
  • hostkeeper.local.v1: Admin on the daemon’s socket.

gRPC and HTTP/JSON, both full. The private listener serves every unary method of hostkeeper.operator.v1 a second time as POST /hostkeeper.operator.v1.<Service>/<Method>, with a proto3 canonical JSON body and Authorization: Bearer <token> (crates/hostkeeper-coordinator/src/grpc/gateway.rs, docs/gateway.md). The gateway is generic. A path is a gateway path when it names a unary method of that package in the embedded descriptors, and the call goes to the same in-process service as gRPC, through the same credential check. So no method exists on one surface and not the other. A body is at most 4096 bytes, but a Releases.SetDesired body, which may carry a release’s targets, at most 256 KiB. A test holds docs/gateway.md’s status table equal to the code’s.

Every declared method has a handler. The PENDING list in crates/hostkeeper-coordinator/src/grpc/mod.rs, of the methods that answer UNIMPLEMENTED until their handler lands, is empty, and a test fails if any method of the command table answers so. Hosts.List answers the hosts a page at a time, by node id.

Credentials. CI authenticates with a GitHub Actions OIDC token, checked against an allow-list (--oidc-config) by crates/hostkeeper-oidc. It allows a clock leeway of 60 s and a token lifetime of at most 600 s by default, and each token is good once. Within the operator API, CI’s token reaches only Releases.SetDesired and Releases.Converge (and their two frozen JSON routes). An operator uses a named bearer token (--tokens-file: names and SHA-256 hashes, re-read while running, so revoking one needs no restart). A token either operates or does not, with no per-token grants. An operator’s token is also admitted on SetDesired, under every refusal CI’s set gets, and on Converge, which changes nothing; the frozen JSON routes stay CI’s (admit in crates/hostkeeper-coordinator/src/grpc/mod.rs).

hkctl is generated from the protos. The build of hostkeeper-proto writes one command per method of every non-local service. hkctl is one bash script emitted from that table, which calls the gateway with curl (crates/hostkeeper-hkctl, docs/cli.md). The test docs_cli_md_is_current regenerates docs/cli.md and fails when it differs, and a golden script makes a removed flag or a changed exit code fail. A release job runs hkctl releases set-desired and then hkctl releases wait-converged, one held call of Releases.WaitConverged (docs/deploy/ci-client.md).

The web UI is built on the gateway. ui/ is static HTML, one stylesheet and JavaScript modules, with no framework and no build step. Its pages are Fleet, Host, Rollout, Holds, Enrollment, Inventory and Audit, and each button is one gateway call made with the operator’s token, held in page memory only. The coordinator serves the files under /ui/ of its private listener when started with --ui-dir (docs/ui-serving.md). The packages do not include the files. The Rollout page sets a service’s desired version with the operator’s token, lists the host groups and moves a host between them, and the Host page lists the services the host runs from Services.List. The Fleet page and the Rollout page’s force dialog read every page of Hosts.List. The UI tests run the app in a JavaScript engine against a fake gateway (crates/hostkeeper-ui-tests), and send every call the app lists in ui/calls.json to the real coordinator, over the gateway and over gRPC with an operator’s token, failing on a call it does not serve or refuses to that token (tests/real_router.rs); the Fleet and Host pages are also tested on a Hosts.List reply that a test of the coordinator holds equal to its answer. The lab section draws each page.

Wire compatibility. the_protos_keep_every_rule_against_the_baseline compares the compiled descriptors with a committed baseline and fails on any removed, renumbered, renamed or retyped field, method or enum value (crates/hostkeeper-proto/src/compat.rs).

Packages

A service version ships as one native package per platform, a .deb or a .pkg (design: native packages). The hook, its bounds, the run units and the health URL are the manifest of the release’s entry, not a file of the package. The platforms are a closed set, linux-x86_64, linux-arm64 and macos-arm64. The daemon knows its own from the target it was compiled for (crates/hostkeeper-config/src/platform.rs).

The targets of a release. CI sets a version with its targets: for each platform an ordered list of entries, one per installer. cargo xtask release targets writes them from the files of the release, and the host installs the entry its daemon announces the installer of, from the project’s package repository (docs/deploy/package-repositories.md). The tree digest and the seal of a placed version are a public format (docs/tree-digest.md).

Signing. Packages are attested in CI. Per commit, artifacts.yml builds the binaries, the packages, deb and rpm, an SBOM, a coordinator image built twice and compared, and an unsigned macOS installer. It attests every file it sums, with a bundle beside each archive, package and installer, and SBOM attestations for the binaries. release.yml publishes a release from main with no manual tag step, once ci, privileged and artifacts have passed on the commit; a failed privileged run holds later releases (.github/workflows/artifacts.yml, .github/workflows/release.yml, docs/deploy/verify-a-release.md). On the host, a pinned gh attestation verify runs offline against the Sigstore trusted root and the config’s one [trusted_signers] entry (organisation, workflow, ref globs, hosted runner). There is no unsigned mode. The bundle is read up to 1 MiB. The pinned gh and the trusted root are read from /usr/lib/hostkeeper/ on Linux and from /usr/local/lib/hostkeeper/ on a Mac (crates/hostkeeper-daemon/src/cli.rs). The deb and the rpm install both on Linux, gh from its release archive checked against a pinned SHA-256 and the trusted root captured when the package is built (docs/deploy/verify-a-release.md); the macOS installer pkg installs both on a Mac (docs/macos.md). A host without them ends every package check attestation_unavailable. Hostkeeper’s own package also carries the trusted root, so each update of hostkeeper brings the root of its release; the daemon uses the copy written last and reports its age in the admin Status (docs/deploy/verify-a-release.md).

Staging. A version is made in a private staging directory under the service’s package directory. The tree is made root-owned and read-only, then sealed: a seal file records its tree digest and package digest, and the version directory appears by rename; a staging directory a crash left is removed (crates/hostkeeper-install/src/version). Before every step the runner re-hashes the staged tree and compares it with the digest taken when the order began.

Versions and links. Each service keeps current and previous links under /var/lib/hostkeeper/packages/<service>/. After a confirmed switch the daemon prunes every other version that nothing still needs. Units are linked from current into the unit directory (/etc/systemd/system, or /Library/LaunchDaemons on a Mac) and files to the paths the manifest names, so one switch of current re-points them all. A write-ahead record, placed.json, lets a crash be repaired at the next start (crates/hostkeeper-placed).

Rollout

Host groups. The coordinator places every host by its host group: a host runs exactly the packages its group lists, and its heartbeat reports at most 16 services (crates/hostkeeper-wire/src/wire.rs). HostGroups.Put creates or replaces a group with its name, its ordered packages (hostkeeper among them) and one rollout policy, and HostGroups.Move moves a host; an enrollment approval names the host’s group (docs/operations/hostgroups.md). The coordinator no longer reads a rollout file: serve refuses --rollout-file, and a fleet placed by roles moves to groups through the operator API (moving a fleet from roles). Services.Assign and Services.Unassign are refused as placed_by_host_group, and an approval that names services as services_retired. Services.SetRepository sets a package’s repository, and Services.SetMinVersion sets a floor for a host or for a group named as the role. A host whose group lists a package it does not run is ordered install of the desired version, under every rule of an update. A package taken out of a group’s list, or a Move, orders the hosts that lose it to uninstall it. Both orders go only to a daemon that announces install-v1, which the daemon’s heartbeat loop does (its features are in crates/hostkeeper-link/src/beat.rs); they reach a host once that loop has a link.

Desired versions. CI sets a service’s desired version with Releases.SetDesired and its OIDC token, and an operator may set it the same way with the operator’s token. Beside the version, a set names the release: the text of the version’s index.json and its SHA-256 (or, for a fleet of one platform, one package digest). The coordinator checks the digest and that the index is the service’s at that version, and keeps the index digest and the package digest of each platform, with the desired state. Each host is then ordered the package of its own platform, and a host whose platform the index lists no package for is ordered nothing and shown as no_package_for_platform, not as failed. A version may instead be set with targets: for each platform an ordered list of artifacts, one per installer. Each host is then ordered the entry of the installer it runs the service with, else the first entry whose installer its daemon lists over gRPC, and a host no entry fits is ordered nothing and shown as no_target, no_build_for_host or installer_dropped, not as failed (crates/hostkeeper-coordinator/src/picks.rs). It refuses a version marked bad or below the service’s min_version. A new desired version ends a standing force and lifts a halt the updater raised, but not one a hook or an operator raised (crates/hostkeeper-coordinator/src/desired.rs, design: The rollout gate).

The update plan. Each heartbeat is decided under one lock, and a reply carries at most one order. A service rolls out by an update plan: a list of stages, each the cumulative percent of the service’s eligible hosts that run the new version once the stage is done, by default four stages (crates/hostkeeper-coordinator/src/stages.rs, design: Rollout update plans). The hosts a stage adds update in parallel, as each heartbeats, up to the desired state’s max_updating per role and never so that fewer live hosts of the role than its min_up stay up. A stage is done when every host in it is up at the desired version and has baked; only then does the next stage start, by itself or, for a stage marked manual, at an operator’s Rollouts.Advance. An operator can Pause and Resume a plan. A host holds an update slot from the moment it is ordered until it has finished and baked. An order the host never reports frees the slot after 120 s. The gate’s rules, first closed rule wins, are halted, held, quiet start, bad version, below min_version, updating, busy with another service, failed here, deferred, the plan’s stage, no slot, below min_up and baking. Releases.Status shows each host’s reason and the plan’s stages. Across services, the coordinator’s --live-rollouts (by default one) is how many services may have a live rollout at once. A service of one host rolls out as one stage, and the rollout of a large service is as long as its stages and bakes, not as its host count.

Canary, bake and automatic rollback. canary = { count = n } is a first stage of n hosts, entered by itself, before the stages of the plan. bake_beats keeps an updated host’s slot until it sends that many healthy heartbeats in a row at the desired version, at most 100. The count is kept in memory, so after a coordinator restart every host bakes again. With rollback = "automatic", release-class failures reaching the larger of a percentage of live hosts and a minimum count mark the desired version bad and set desired back to the last version that converged and baked (crates/hostkeeper-coordinator/src/reconcile.rs). That rollback goes out as an ordinary update to the lower version. The daemon refuses an update below the version it runs (below_running), so a host that already took the bad version is not moved back by it. Releases.Force is the operator’s repair.

Holds. Services.Hold holds one service on one host, on a role or on the whole fleet, with a reason (docs/operations/holds-and-force.md). A held pair is ordered nothing, takes no slot and is never a canary. At most 4096 holds are kept, and they survive a restart. Hosts.Exclude takes a host out of a service (with abandon, it also frees the host’s slot at once).

Force and abort. Releases.Force orders a hookless force of a service to a version on the whole fleet, a role or named hosts, at each target’s next heartbeat, past the update plan, canary, bake, bad marks and halts. The daemon fetches the package if needed, stops the old units, switches current, links, starts the new units and reports, running no hook (crates/hostkeeper-coordinator/src/force.rs, crates/hostkeeper-daemon/src/verbs/force, design: Force). A force reaches only hosts that have already announced the service in a heartbeat. It is refused for the hostkeeper service itself and for a version no set ever registered a digest for. Hosts.Abort is accepted and audited. The coordinator sends it only to a daemon that announced abort-v1. The daemon’s heartbeat loop announces it and runs the abort beside the order it stops, whose verdict then reports the halt; on a host the coordinator cannot reach, root stops the daemon.

The audit trail. Every change to the ops store is one entry: who (operator token name, ci or coordinator), the action, the service, the host and the reason. In the database the entries are rows of the table audit, which refuses every update, delete and truncate; a change commits its row in the same transaction as the change (an enrollment approval writes it just after), and every row is kept. A change whose transaction fails is refused store_failed, except one that raises protection (a halt, a bad mark, a pause, an abort), which stands in memory under the marker until it lands. On the file store they go to an append-only audit file, one JSON line each, fsynced, rotated by size: a full file is sealed as a numbered segment on a line boundary, the numbers go on across files, and the oldest segments past a retained count are deleted. There a change is not made without its line: when it cannot be appended the call is refused with audit_unavailable, except Hosts.Abort and Releases.Halt, which stand with the failure logged. The coordinator keeps the last 64 entries for Releases.Status. On the database store Audit.List reads a page of the table audit. On the file store it reads the active file and the segments kept a chunk at a time, never a whole file (crates/hostkeeper-coordinator/src/audit_file.rs): the first entry after since_seq is found by bisection, and the newest entries by reading back from the end of the newest file. It filters by actor, token name, action, service and host, at most 256 entries a page (crates/hostkeeper-coordinator/src/operator.rs). A SetDesired by CI without targets writes no audit entry of its own (only the force it ends, force_ended, and the halt it lifts, lift_halt, are audited as ci); one with targets is a set_desired entry as ci, naming each entry’s digest and its manifest’s; one made with an operator’s token is a set_desired entry under the token’s name (set_desired_by in crates/hostkeeper-coordinator/src/service_ci.rs). An entry that Audit.List answers carries its time and the name it was made under; the entry in a change’s own answer has the name and no time. Enrollment’s own changes are audited under coordinator: a new request (enroll_requested), a certificate’s first issue (enroll_issued), a renewal (cert_renewed) and a request that expired (request_expired), with no CSR, key, nonce or signature in the reason.

Update hooks

The step contract is in crates/hostkeeper-hook (design: How a hook runs, host-updates: The step contract). A service’s hook is an executable in its package, named by the manifest’s [hook] command. An update runs prepare, cutover, verify and cleanup, and runs rollback after a failure. Each step gets the step word, the staged release (to prepare only) and --params <file>, a TOML file of the manifest’s [params] plus reserved updater.* keys. The leading arguments of the manifest’s command are not passed to these steps, only to the boot and uninstall steps (crates/hostkeeper-daemon/src/verbs/update.rs), so a hook must accept the bare step word. Its exit code is 0 for success, 1 for failure, 75 for deferred and 76 for halt. Any other code, a signal or a timeout is a failure. The last stdout line, read up to 64 KiB, is an optional JSON report: class release or environment, a reason, retry_after_secs, reversible and promotion_pending. The last 1024 KiB of each stream is kept. Each step’s bound comes from the manifest’s [hook.timeout_secs]. Only prepare may be unbounded, and the daemon has no default. The phase of a failure is decided by the updater, never by the hook: before commit, at the gate, after commit (once a step said reversible: false), or halt.

The step launcher. On Linux, SystemdLauncher runs each step as root in a transient unit, systemd-run --system --wait --collect --pipe --unit=updater-<service>-<step>-<generation> --property=RuntimeMaxSec=<secs|infinity>, with no other property: no user, no capabilities, no sandbox (crates/hostkeeper-steps/src/systemd.rs). A dead-man thread polls every 1 s and stops a unit by name at its deadline, and RuntimeMaxSec still ends it if the daemon has died (design: The dead-man). On macOS, LaunchdLauncher runs each step as a transient launchd job in the system domain. launchd has no RuntimeMaxSec, so the launcher polls the job every 500 ms and boots it out at its bound (crates/hostkeeper-launchd/src/launcher.rs). That bound is the launcher’s alone: if the daemon dies, a bounded step runs on until the restarted daemon finds it in its record and stops it. Either way a step stopped at its bound has no exit code and is a failure. Neither launcher runs the "additive" steps yet (a manifest’s boot step, the hook’s uninstall step, the self-update probe): both refuse to start them.

The step record (step-record.json under /var/lib/updater/state/<service>/) is written running before each step and done after it, with an fsync and a rename. After a daemon crash the running step’s unit is stopped by name and the step runs again. After a reboot (a new boot id), an uncommitted update is rolled back and a committed one goes on to verify with a fresh window (crates/hostkeeper-steps/src/resume.rs, design: The step runner).

How a failed verify rolls back (crates/hostkeeper-hook/src/next.rs, crates/hostkeeper-daemon/src/place.rs): verify has its own window, from the end of cutover to verify_deadline_secs. A verify that exits non-zero, or still defers when the window ends, sends the runner to rollback. Before running the hook’s rollback, the daemon points current back at the previous version and relinks that release’s units and files. On a first install it removes the links instead. Then it runs the new release’s rollback step, and the host reports Failed at the gate phase (after the commit, if a step had said reversible: false) with the rollback’s reason, or else verify’s. Restarting the old service is the hook’s job. A deferred rollback is retried 3 times, after retry_after_secs or 60 s by default, and never more than 3600 s. A rollback that fails, or still defers after those retries, is a halt (the service takes no further order until the halt is cleared), unless its report says reversible: false, which makes it Failed after the commit; a first install whose rollback declines with no_previous_release ends Failed. A failed cleanup that says reversible: true before any commit sends the update to rollback; any other failed cleanup is retried 3 times by default (the hook’s cleanup_retries), then ends Failed after the commit. A hook that reports promotion_pending is watched after success: verify runs again after its retry_after_secs, or every 30 s by default, until it passes without the flag. Any other result, or the ceiling, ends the update Failed after the commit (or a halt), and the watcher never rolls back (design: The post-success watcher).

The unit control on Linux. The switch before cutover runs daemon-reload through the adapter set’s unit control, and a force or a rollback stops and starts units through it. On Linux that is hostkeeper-placed’s Systemctl, each call one systemctl command run as a child process of the daemon, as root, bounded by 300 s (crates/hostkeeper-daemon/src/adapters.rs). The macOS adapter set has a launchd unit control: a reload bootstraps the job of each placed plist link that is new or re-pointed, booting it out first when it is loaded, and boots out the job of a link that is gone.

The example service. examples/hello is a loopback HTTP server with an update hook and two unit slots that it swaps at cutover (docs/hello.md). Its -fail-ready build answers its readiness check with an error, so its verify fails and its rollback restarts the old slot. That is the case the rollback measurement uses. hello is not run through the conformance harness in this repository.

macOS specifics

The same daemon runs on Apple silicon (macos-arm64; an Intel Mac is not a platform). The adapter set is chosen when the binary is compiled (crates/hostkeeper-daemon/src/adapters.rs, docs/macos.md, design: macOS):

  • launchd runs the daemon as dev.hostkeeper.hostkeeper from /Library/LaunchDaemons, with KeepAlive. Hook steps are transient launchd jobs bounded by the launcher, as above (crates/hostkeeper-launchd).
  • Service state comes from launchctl print. A process is identified by its pid and start time, and its executable by the device and inode of the image it runs, so a binary renamed over while it runs is not mistaken for the running one.
  • Every unpacked package is checked for the quarantine attribute, and every Mach-O file must carry a valid code signature (ad-hoc accepted; no team identity or notarisation check).
  • Enrollment claims are the serial number and platform UUID from ioreg.
  • Self-update: launchd has no start limit and the daemon arms no fallback job. The old binary hands over to the new one and, after 3 starts of it that do not settle the update, settles the update failed and runs.
  • The installer is an unsigned distribution .pkg (productbuild around one component pkg) holding the binary, the daemon’s plist, its log directory and newsyslog file, the pinned gh and the Sigstore trusted root. Its postinstall loads the daemon’s job, whose program is the installed binary: each start seeds the binary directory, writes hostkeeper.toml from the MDM’s managed preferences when it is absent, and execs current.

The macos-device job of .github/workflows/release.yml runs as root on a hosted Mac after each merge to main. It shows real codesign and quarantine verdicts, the process identity check, launchd job states, a fixture hook stopped at its bound, and the daemon started under launchd answering Status, and, end to end, hello’s package installed, updated, rolled back on a failed verify and uninstalled by the daemon under launchd, enrolled with and ordered by a coordinator in the test. Not built for Macs: MDM, the boot id that tells a reboot from a daemon restart (it is read from a Linux path), version confirmation by executable digest, and support files at macOS paths (the CA bundle, gh and the trusted root use their Linux paths).

Case study

Our lab, the worked example

Our lab is where hostkeeper runs first, and where the measurements of the last section are taken. This section shows how the lab is laid out, how its machines are described to hostkeeper, and how an operator sees it in the UI. The lab is described generically: the machines are named node-1 to node-6 and mac-1 and mac-2, and no hostname, address or serial of a real machine appears. So far hostkeeper has adopted and enrolled the six Linux nodes, node-5 first as a canary and then the other five; it installed, updated and rolled back the hello service on node-5 and installed it on the other five. What follows is the lab as hostkeeper is set up to keep it, and the last section has the times of those runs.

The topology

The lab has six Linux servers that are both build and storage nodes, and two Mac Studios. A management network reaches every machine and every server’s BMC. A separate storage network joins the six Linux nodes, for the storage traffic between them. The coordinator runs in a container on a separate development machine on the management network, and its database in another container on the same machine. CI runs on GitHub-hosted runners outside the lab and reaches the coordinator’s private listener, and nothing else: no host has an inbound port, and the runners hold no ssh key.

Case study

The coordinator in a container is the shipped image (packaging/container/Dockerfile): a distroless image that runs as a non-root user, takes all its configuration as arguments and sets no environment variable. Its database is a Postgres server in another container on the development machine, which the lab’s other services share: the coordinator reaches it by the server’s Unix socket, mounted into its container, and reads the connection string, with the password, from a secret file (--database-dsn-file), never from its arguments. The coordinator moved there from its file store with a verb since removed; its CA key and server certificate are still files on its volume. Its private listener refuses a wildcard address, so it binds one interface of the development machine. The reusable workflow that CI calls is described in docs/deploy/ci-client.md.

How machines are labelled: MAC address, host record, role, services

A machine is known to hostkeeper in four steps, each kept by a different hand:

  1. MAC address and serial. When a server is built, the operator records its data MACs and its BMC MAC, and for a Mac its serial. These are what the machine says it is when it asks to enroll: a Linux daemon claims its network addresses, machine id, DMI serial and BMC MAC, and a Mac claims its serial and platform UUID. A claim is written by the requester, so it proves nothing.
  2. Host record. The record (Enrollment.AddRecord, the Inventory page) gives the machine its host id and its expected role. A pending request whose claimed addresses include a record’s data MAC (or, for a Mac, whose serial is the record’s) shows that record’s host id and role on the Enrollment page. The match fills in the approval form; it approves only when the record is open, unused and names a role, the match is exact and uncontested, and the request arrives within the record’s window, and then once.
  3. Role. The operator approves the request by its key hash, with a host id and a role. The role goes into the host’s certificate, and the coordinator reads it from there on every connection.
  4. Host group. The approval names the host’s group, and the host runs the packages that group lists. HostGroups.Move changes it later.

Correctness and failure handling

What the code does when a part fails, and how it is tested. The failure cases are the ones the problem starts from: a run that stops midway, a host or a coordinator that dies, a hook that hangs or lies, and two updates at once.

Failure model

What the code does, by failure (design: Races and failures):

  • The coordinator dies or is unreachable. Steps already running need no coordinator. Each runs on its own thread, bounded by the dead-man and its unit, and its verdict waits in memory to be sent with a heartbeat that works. The heartbeat loop beats on a fixed period, with no backoff. A restarted coordinator keeps its store (desired state, ops, halts, verdicts, spent tokens, enrollment store) and forgets the fleet. Its rollout gate and automatic rollback order nothing for a quiet start of at least 30 s, while it hears every host again; a standing force is resent at once. Bake counts, deferral backoff and queued aborts start from zero. A halt is written under a marker, and a start that finds the marker is refused until an operator settles it. There is one coordinator and no failover.
  • A host dies or reboots mid-step. The step record and the boot id decide (see Update hooks). A second daemon on the same state directory exits at once on the state lock. On the coordinator, a host silent for 45 s is down. A down host that was updating keeps its update slot until it returns or an operator excludes it with abandon.
  • A hook hangs, fails or lies. A hang is stopped at its bound and is a failure. A failure before commit is rolled back. The halt exit code, or a rollback that fails (see Update hooks), halts the service on that host until cleared, and the coordinator halts the service fleet-wide. A step that cannot be stopped keeps the service locked until an operator aborts it with hkctl hosts abort (the coordinator’s Hosts.Abort does not reach the shipped daemon), and an abort tries the stop 3 times. A hook that passes verify while its service is down is not caught by the daemon. The coordinator notices it only through bake (bake_beats above zero), and automatic rollback reads reported failures, never unhealthy heartbeats. Nothing confines a hook: it is root, and its limits are the trusted signers and the conformance suite, not the daemon.
  • The network fails. The daemon resends a verdict in every heartbeat until the coordinator acknowledges it, but the resend queue is in memory, so after a daemon restart the verdict comes back from the step record when the coordinator orders again. A heartbeat is at most 16 KiB. A host away past its certificate’s expiry must be approved again. A coordinator renews its own server certificate while it runs; one whose renewals keep failing (shown in the status) is refused by every daemon once the certificate in use expires.
  • A bad package. Fetch, digest, attestation and unpack failures refuse the order before any hook runs. One difference from the design: on a hooked order, a transient fetch or attestation failure reaches the coordinator as Failed with the reason, not as Deferred (crates/hostkeeper-daemon/src/link_adapters.rs).
  • Two updates at once. A host runs one order per service at a time and one step at a time. The update plan orders a stage’s hosts only up to the role’s max_updating. A force takes over from a running update by stopping its step, with no rollback.

Testing

Every crate of the workspace must reach Percent::TARGET, 9,900 hundredths of a percent, of its lines and of its branches, judged by coverage-gate in CI’s test job with no exclusion list (crates/coverage-gate, AGENTS.md).

  • The privileged real-systemd suite. .github/workflows/privileged.yml runs as root on a hosted Ubuntu runner after each merge to main. It is never run on a pull request and counts toward no coverage gate, but a release waits for it to pass on its commit. Its tests (crates/hostkeeper-privileged/tests) drive the production adapters against real systemd: a step in a real transient unit ended at its bound with its whole control group, RuntimeMaxSec as the only property, an unbounded prepare, the dead-man stopping a unit by name, a unit name reused after a failure, long output kept to its last bytes, and the observer reading a real unit’s state and its main process’s executable digest. The workload is hostkeeper-fixture-hook. Its job first-boot runs the programs themselves: the coordinator and the daemon started as child processes on loopback and driven through the generated gRPC clients. first_boot.rs covers an enrollment, its approval, the host certificate, heartbeats over mutual TLS, a restart of each program, and a renewal: with the coordinator started with --host-cert-validity-secs 60, the daemon renews its certificate for the same subject and key and is heard over the renewed one. install_uninstall.rs covers a package installed through a host group once across coordinator restarts, and kept by the daemon’s boot pass, from a release channel the test serves over HTTPS, then updated to a new desired version, then uninstalled by the operator: the package, its placed file and its unit are taken off the host. Its one stand-in is the attestation verifier, true in place of gh. On macOS, the macos-device job above is the only test that runs the daemon binary under launchd.
  • End to end, in process. crates/hostkeeper-daemon/tests/end_to_end.rs runs the real coordinator, heartbeat loop, executor, step runner and boot pass together, with fakes for the transport, the service manager and the package source: a desired version set on the coordinator reaches a fixture hook and reads converged. crates/hostkeeper-daemon/tests/hello.rs runs hello’s real hook through the daemon for an install, an update and a failed update that rolls back. crates/hostkeeper-coordinator/tests/farm.rs runs the coordinator behind real mutual TLS over in-memory streams. No test runs a daemon and a coordinator as two processes over a network.
  • Conformance. A service tests its own hook with the harness behind the conformance feature of hostkeeper-hook (docs/conformance.md). The harness runs the real hook executable against the service’s fake and checks exit codes and reports, repeated steps, rollback restoring the world, a kill at every kill point, the updater’s next-step table, and the record-directory lock. It is shown refusing deliberately flawed hooks (crates/hostkeeper-hook/tests/conformance.rs).
  • Lints run as tests in xtask. The workflow lint pins runners, triggers, permissions and action pins, and keeps root jobs in privileged.yml. The wall-clock lint allows a wall-clock read only where a reason is listed. The hygiene lint covers this public repository’s text. The layering lint holds each crate’s dependencies. This report’s own check is also among them.

What is not built yet

What is not built, plainly:

  • Orders the daemon takes: the heartbeat loop runs update, force, install, uninstall and abort, and announces install-v1 and abort-v1, so the coordinator’s install, uninstall and Hosts.Abort are sent to it over the heartbeat link, once the host has its certificate (identity and enrollment). The loop runs no force_rollback or clear_halt, and the coordinator never orders them.
  • Rollout shape: the update plan is the host group’s policy, which a Put changes without a restart. Automatic rollback cannot move a host back below the version it runs.
  • Identity: no BMC reader, no operator call to deny or retire a host, no CA rotation or revocation lists.
  • Operations: a single coordinator with no failover; on the file store the audit keeps only its retained segments, so the oldest entries are deleted (in the database every row is kept); there is no metrics endpoint and no pager (conditions that need a person are alert= log lines and Alerts.List).
  • macOS: no MDM, no update run on a device, no signed installer.
  • A hook is root and is not confined. This is by design: the trust is in the signed package and the conformance suite (design: Limits).
  • Distribution: releases are published as GitHub releases, but no release channel is hosted.

The design’s plan for the rest is its build order (design: Build order). High availability for the coordinator, hardware-backed identity and power control through the BMC are not planned there (design: Not planned).
